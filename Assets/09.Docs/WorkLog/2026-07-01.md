## 작업 3 — Phase ARCH-2: 핵심 5종 Behavior 추출

### 대상
기존 SkillExecutor.ExecuteAttack의 if문 중 가장 복잡한 5종. 각각을 독립 클래스로 추출.

### 신규 파일 (5개 — 구현체, `02.Scripts/Skill/Behaviors/Implementations/`)

| 클래스 | Phase | Order | 캡슐화한 로직 |
|--------|-------|-------|------------|
| `BerserkBehavior` | PowerModify | 50 | HP 50% 이하 시 위력 × 2 (기존 line 107-112) |
| `PierceBehavior` | DamageApply | 10 | 쉴드+DEF 무시, TakeDirectDamage. ctx.SkipDefaultDamage=true 설정 (기존 line 170-189) |
| `ExecutionBehavior` | PostDamage | 10 | HP rank 이하 처형, 보스 제외 (기존 line 191-202) |
| `LifestealBehavior` | PostDamage | 50 | ctx.LastActualDamage/2 회복 (기존 line 204-211) |
| `ChainBehavior` | PostDamage | 200 | 무작위 N명 연쇄, rank=연쇄 수 (기존 line 225-239) |

### Order를 통한 Phase 내 순서 보장
PostDamage Phase 내에서 Execution(10) → Lifesteal(50) → Chain(200) 순서로 실행. 이것은 기존 ExecuteAttack의 코드 순서와 동일 (Pierce → DealDamage → Execution → Lifesteal → Chain).

### 핵심 설계 포인트
- 각 Behavior는 **자신의 Keyword에 대한 로직만 캡슐화** — 다른 Behavior의 존재를 모름
- ctx.LastActualDamage로 Behavior 간 간접 통신 (Lifesteal이 Pierce/Execution의 데미지 기반 회복)
- Pierce가 ctx.SkipDefaultDamage=true 설정 → Pipeline은 기본 DealDamage를 스킵
- Execution은 PostDamage에서 체크 (Pierce/기본 DealDamage 이후 남은 HP 기준)

## 핵심 아키텍처 통찰

### 진정한 "조립식"이란
- **데이터 계층**은 Phase BK에서 이미 완전 조립식 (`SkillData._behaviors: BehaviorTag[]`)
- **로직 계층**이 하드코딩에서 벗어나려면 **각 Behavior가 독립 클래스**로 존재해야
- 새 키워드 추가 시 `SkillExecutor` 코드 수정 0줄 = Open-Closed 원칙 달성
- 각 Behavior의 단위 테스트가 독립 가능 → 품질 향상

### 파이프라인 패턴 선택 이유
- Strategy 패턴 + Decorator 패턴 + Data-Driven Pipeline의 하이브리드
- 각 Behavior가 자신의 개입 Phase(ExecutionPhase Flags)를 스스로 선언
- Pipeline은 정해진 Phase 순서대로만 호출 — Behavior 간 결합도 최소
- Order 프로퍼티로 같은 Phase 내 세부 순서 제어 (예: Execution이 Lifesteal보다 먼저)

### 병행 구조의 안전성
- 기존 SkillExecutor.ExecuteAttack을 **당장 교체하지 않음** — 회귀 위험 큼
- 새 Pipeline은 별도 클래스로 작성만 하고 호출 안 됨
- ARCH-3에서 충분한 테스트 후 ExecuteAttack 교체 (점진적 전환)

## 작업 5 — Phase ARCH-3: 기존 19종 Behavior 추출 + ExecuteAttack 교체

### 배경
Phase ARCH-1/2에서 뼈대와 5종 핵심 Behavior를 만들었지만, 병행 구조(Pipeline은 존재만 하고 호출 안 됨)를 종료하려면 SkillExecutor.ExecuteAttack의 로직을 Pipeline으로 실제 이관해야 함.

### 안전한 타협안
TurnManager의 타겟팅 분해(Spread/Bounce/MultiHit/Explosion/AOEAuto)는 **TurnManager에 그대로 유지**. Pipeline.ExecuteAttack은 **단일 타겟에 대한 처리만** 담당 (위력 계산 + 데미지 적용 + 후처리). 이렇게 하면 회귀 위험 최소화하면서 병행 구조 종료.

### 변경 내역

#### A. Touch 3종 Behavior 추출 (`Implementations/TouchBehaviors.cs`)
- `VenomTouchBehavior` / `BurningTouchBehavior` / `FreezeTouchBehavior` (PostDamage Phase, Order 100/110/120)
- 기존 `SkillExecutor.ApplyTouchEffects` 로직을 각 Behavior의 `OnPostDamage`로 이관
- rank = 부여할 상태이상 스택 수

#### B. BehaviorRegistry 등록
Touch 3종 추가 등록. 코멘트로 Phase 별 보류 항목(TurnManager 담당/EffectivePower 간접 처리 등) 명시.

#### C. SkillExecutionPipeline.ExecuteAttack 완전 확장
기존 `SkillExecutor.ExecuteAttack` (line 99-257)의 **모든 로직**을 Pipeline에 1:1 이식:
- PowerModify Phase + 글로벌 훅(키워드 conditionalMul, 유물 relicPowerMul, 유물/특성 lowHPMul, 유물/특성 nextBonus, 대상 takenMul)
- DamageApply Phase (Pierce)
- 글로벌 훅(유물 healPercent)
- PostDamage Phase (Execution → Lifesteal → Touch 3종 → Chain)
- OnKill Phase + 글로벌 훅(유물/특성 killHeal)

#### D. SkillExecutor.ExecuteSkillInternal 수정
